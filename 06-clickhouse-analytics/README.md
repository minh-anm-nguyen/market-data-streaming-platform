# Project 06 — ClickHouse Time-Series Analytics & Materialized 1m OHLC Bars

Implementation of [`docs/PROJECT_06_ClickHouse_Time_Series_Analytics_System_Design.md`](../docs/PROJECT_06_ClickHouse_Time_Series_Analytics_System_Design.md).

Reads the Project 05 raw landing table, reconciles it against a sealed source
snapshot, stages an immutable canonical candidate, derives 1-minute tick OHLC
bars through an `AggregatingMergeTree` materialized view, verifies those bars
against an independent Python oracle, and publishes a `build_id` only if every
proof holds.

Correctness order, from the design: **correctness → never publish something
wrong → be able to reconcile → bounded resources → recovery → performance.**

## What the golden case looks like

Section 16.1, asserted byte for byte in `test_e2e_01_six_event_golden`:

```
Dataset GOLDEN-01, EURUSD, price_scale = 100000
  tick  12:00:00.000000000  seq=1  price=100000
  quote 12:00:20.000000000  seq=2  bid=100010 ask=100012
  tick  12:00:30.000000000  seq=3  price=100200
  tick  12:00:30.000000000  seq=4  price=99900
  quote 12:00:45.000000000  seq=5  bid=99950  ask=99952
  tick  12:01:00.000000000  seq=6  price=100100

bar [12:00, 12:01)  O=100000  H=100200  L=99900  C=99900  tick_count=3
bar [12:01, 12:02)  O=100100  H=100100  L=100100  C=100100  tick_count=1
```

`CLOSE = 99900`, not `100200`: ticks 3 and 4 share a timestamp, so the
**sequence** breaks the tie and the later sequence closes — not the higher price.
The two quotes contribute nothing: a quote is not a trade, and its ask must
never reach a tick HIGH.

## The four ideas that drive the design

**1. Identity is `(dataset_id, symbol, sequence)`.** Kafka topic, partition and
offset describe *transport*. A replay through a different partition topology
produces the same identities. Same identity + same semantic core is a physical
duplicate, which at-least-once delivery makes normal. Same identity + a
*different* core is a `CONFLICT` and stops the build — `argMax(ingested_at)`
would pick the most recently written row, which has nothing to do with which one
is true.

**2. `MergeTree` does not enforce uniqueness.** `ORDER BY` is a sorting key and
an index, not a constraint. "One row per identity" is produced by the builder and
then *proved* by an independent check. A successful INSERT is not evidence.

**3. The materialized view is an insert trigger over blocks.** One block yields
one partial aggregate state per bar; a second block covering the same minute
yields another. Readers must finalize with `*Merge`, and the suite asserts the
answer is identical before and after a merge rather than assuming it. Nothing
de-duplicates logical events, so inserting the same canonical row twice doubles
`tick_count` permanently — which is why an unknown acknowledgement marks a build
`DIRTY` instead of triggering a retry.

**4. `tick_count` is not volume.** P02 ticks carry no trade size. There is no
`volume` field anywhere, and a test asserts there never will be.

## Verdicts and exit codes

`PASS` is the only value reported as success. The CLI maps verdicts to distinct
exit codes so a CI job can tell a refusal from a crash:

| Code | Verdict | Meaning |
|---:|---|---|
| 0 | `PASS` | proven |
| 1 | `FAIL` | an invariant was violated |
| 3 | `NO_GO` | refused to publish — **often the correct behaviour** |
| 4 | `INCONCLUSIVE` | not proven either way, which is not a pass |

A job that treats every non-zero code as a crash will eventually be "fixed" by
removing the refusal, which is why `NO_GO` has its own code. Eight of the 32 E2E
tests pass *by* the pipeline declining to publish.
